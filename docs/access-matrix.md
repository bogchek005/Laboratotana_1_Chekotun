\## Правила авторизації



1\. Усі перелічені операції потребують автентифікації.



2\. Reporter переглядає тільки власні інциденти.



3\. Analyst може переглядати інциденти для аналізу,

&#x20;  незалежно від власника.



4\. Administrator має доступ до передбачених матрицею

&#x20;  адміністративних операцій.



5\. Власник визначається через перевірений principal,

&#x20;  а не через дані HTTP-запиту.



6\. Звичайний update не змінює OwnerUserId,

&#x20;  Status або інші server-managed поля.



7\. Зміна статусу через triage доступна лише

&#x20;  Analyst та Administrator.



8\. Internal comments не повертаються Reporter.



\## Політика HTTP-відмов



401 Unauthorized:

користувач не автентифікований.



403 Forbidden:

автентифікований користувач не має дозволеної ролі

для привілейованої операції.



404 Not Found:

інцидент не існує або недоступний користувачу

відповідно до правила ownership.



Для чужого інциденту Reporter отримує однакову

відповідь 404, як і для неіснуючого інциденту.



\## Обґрунтування політики 404



Для доступу до чужого інциденту обрано

404 Not Found, оскільки звичайний Reporter

не повинен отримувати підтвердження

існування ресурсу іншого користувача.



Однакова відповідь застосовується до:

\- GET /api/incidents/{id}

\- PUT /api/incidents/{id}

\- DELETE /api/incidents/{id}



Для неіснуючого та чужого ресурсу

мають збігатися HTTP status, Content-Type

і тіло відповіді.



Для privileged action /triage користувач

без необхідної ролі отримує 403 Forbidden.



Анонімний користувач отримує

401 Unauthorized незалежно від identifier.



Усі рішення приймаються на сервері

після перевірки principal.



\## Привілейована дія: triage інциденту



Endpoint: `POST /api/incidents/{id}/triage`



Призначення: переведення інциденту зі стану `New` у `Triaged`.



Правило авторизації: операцію дозволено користувачам із ролями `Analyst` та `Administrator`. Користувач із роллю `Reporter` не має права виконувати цю операцію, навіть якщо він є власником інциденту.



Контекст ресурсу: перед зміною стану сервер перевіряє, що інцидент існує та його поточний статус дорівнює `New`. Наступний статус `Triaged` визначається сервером, а не значенням із тіла HTTP-запиту.



Правило володіння: для ролі `Reporter` володіння інцидентом не надає додаткового права на triage.



Захист від підміни полів: значення `role`, `OwnerUserId`, `status` та `isTransitionAllowed`, передані клієнтом, не можуть впливати на рішення про авторизацію.



Аудит відмови: при забороненій спробі виконання triage сервер має записати подію `authorization.denied`, яка містить ідентифікатор автентифікованого користувача, дію, ідентифікатор ресурсу, результат, час події та trace id запиту без паролів, cookie, токенів і повного HTTP-body.
