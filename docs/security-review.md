## 1\. Executive summary

Виконано комплексний огляд навчального застосунку SecureLab після ЛР №5: браузерний клієнт, API, автентифікація, CSRF-захист, rate limiting, NuGet-залежності, Git-файли, журнали та аудит привілейованих операцій. Фактичні докази включають відхилення змінювальних запитів без CSRF-токена (HTTP 400), незмінність даних після таких відмов, позитивні POST 201 і triage 204 із валідним токеном, блокування четвертого search-запиту кодом 429 після трьох дозволених, відновлення доступу після вікна, аудит NuGet без повідомлених вразливих пакетів та аудит логів.

Оформлено дві знахідки: **F-01** — реальний навчальний пароль у tracked HTTP-тесті; **F-02** — необхідність antiforgery validation на cookie-authenticated mutation endpoints, яку усунуто явним фільтром. F-01 підтверджено скриншотами знаходження і виправлення, F-02 — кодом захисту та негативними й позитивними HTTP-сценаріями. Пароль з попередніх commits вважати потенційно доступним до ротації та окремого очищення історії.

## 2\. Scope and exclusions

**У межах огляду:**

* API маршрути `/api/auth/login`, `/api/auth/logout`, `/api/auth/csrf-token`, `/api/me`, `/api/incidents`, `/api/incidents/{id}`, `/api/incidents/{id}/triage`, `/api/incidents/search`;
* `Program.cs`, `IncidentEndpoints.cs`, `Lab02Endpoints.cs`, `Lab03Identity.cs`, `AntiforgeryFilter.cs`, `csrf-helper.js` і клієнтські HTML/JS-файли;
* налаштування HTTP security headers, CORS, antiforgery, авторизації та обмеження частоти запитів;
* прямі й транзитивні NuGet-пакети, поточні tracked Git-файли, вибіркова історія підозрілого файлу;
* локальний журнал API та structured audit event `incident.triage`.

**Поза межами:** сторонні сервіси, зовнішні системи й реальні облікові записи; повний аудит усієї Git-історії, stash та інших клонів; перевірка доступності у Production та penetration test; незафіксовані в рисунках результати тестів. Усі перевірки виконуються тільки на власному локальному стенді зі штучними даними.

## 3\. System overview and trust boundaries

Застосунок складається з браузерного клієнта, ASP.NET Core API, Identity/cookie authentication, сервісів логування та PostgreSQL. Користувачі Alice і Bob мають роль Reporter, Morgan — Analyst. Дані надходять від браузера до API, де повинні пройти authentication, authorization, antiforgery validation (для визначених mutations), валідацію та перевірки доступу до ресурсу; далі виконується операція з БД.

**Межі довіри:**

1. Браузер / мережа → API: вхідні URL, JSON, cookie, заголовки та request token не є автоматично довіреними.
2. Автентифікована сесія → роль / власність інциденту: коректна cookie не надає доступу до чужого ресурсу та privileged triage.
3. API → PostgreSQL: доступ обмежено локальною конфігурацією; credentials не повинні зберігатися у tracked файлах.
4. API → журнали: необхідно записувати метадані без password, cookie, request token і повних моделей.
5. Браузерний origin → CORS/CSP: browser controls не замінюють server-side authorization.

## 4\. Methodology and test environment

Використані Visual Studio 2026, PowerShell, dotnet CLI, Git і DevTools браузера. Зафіксовано запуск API на `localhost:5080` у профілі Debug, процес `SecureLab.Api.exe` і проходження breakpoint в antiforgery-фільтрі. Під час крокового виконання ValidateRequestAsync потрапив у `catch (AntiforgeryValidationException)`, що узгоджується з фактичними HTTP 400 при запитах без request token.

Методика: зафіксувати baseline → виконати негативний сценарій → внести вузьку зміну → повторити негативний сценарій → повторити дозволений позитивний сценарій → зберегти очищені докази. Візуальні результати наведені у звіті ЛР №6, зокрема рисунки 21–28, 46–74, 75–79 та 80–92.

## 6\. Detailed findings

### F-01 — облікові дані в tracked HTTP-тесті

Команда `git grep` виявила буквальне значення навчального пароля в `tests/SecureLab.Api.Tests/lab-03-tests.http`, рядок 4 (рисунок 82). Значення замінено змінною середовища `SeedUsers\_\_Password` (рисунок 83), а зміну зафіксовано комітом (рисунок 85). Релевантну історію файлу переглянуто окремо (рисунок 84). Подробиці — у `docs/findings/F-01-hardcoded-password.md`.

### F-02 — antiforgery validation на змінювальних маршрутах

У фінальному варіанті підключено стандартний ASP.NET Core antiforgery, endpoint видачі request token і `AntiforgeryFilter`; для PUT/DELETE додано явний фільтр (рисунки 21–28, 46). POST без токена повернув 400, після відмови інцидент не створився, позитивний POST із токеном — 201, PUT/DELETE без токена — 400 зі збереженням ресурсу, logout без токена — 400, дозволений logout — 204, triage без токена — 400, дозволений triage — 204 (рисунки 48–74). Подробиці — у `docs/findings/F-02-csrf-mutations.md`. Для остаточної відтворюваності первинного дефекту рекомендовано додати точний hash baseline.

## 9\. Dependency and secret audit

### NuGet

Виконано `dotnet restore` та `dotnet package list --vulnerable --include-transitive`. Вивід показує, що для API і тестового проєкту відомих vulnerable packages за поточними джерелами не повідомлено (рисунки 80–81). До джерел належать NuGet.org і локальні пакети SDK. Не можна робити висновок про відсутність усіх можливих вразливостей. **Decision:** наразі оновлення через advisory не обґрунтовано. У разі появи advisory потрібна таблиця direct/transitive, severity, reachability, fixed version і decision.

### Git secret scan

Команда `git grep -n -I -i -E 'password|passwd|secret|api.?key' -- .` виявила буквальний пароль у `lab-03-tests.http` (рисунок 82). Внесено виправлення шляхом звернення до `SeedUsers\_\_Password` (рисунок 83). Інші збіги включали назви полів форм, методи автентифікації, навчальний пароль PostgreSQL у локальному compose, тестові заглушки й імена змінних. Кількість усіх унікальних збігів не підтверджена окремим підрахунком; у звіті не вигадується. Повна Git-історія, stash та CI не сканувалися.

### Audit/log review

Додано structured `audit.event` після успішного triage зі значеннями Subject/Action/Resource/Result/Time (рисунки 86, 89). Перевірка демонстраційного неправильного пароля, назви Cookie-заголовків та назви CSRF-заголовка в локальному логу дала 0 збігів за відповідними шаблонами (рисунки 90–92). Відсутність *фактичного* seed password у логах окремим доказом не підтверджена, так само як і всі шість сценаріїв журналювання.

## 10\. Residual risks

1. Hardcoded seed password міг залишитися в старих Git-комітах або копіях; потребує ротації та обережної оцінки історії.
2. Немає повного підтвердження, що Bob з іншим user ID має незалежну квоту під час блокування Alice.
3. Немає повного нового regression pack усіх напрямів ЛР №2–5 після фінальних змін.
4. Немає фінального виводу `dotnet test` після останнього commit, merge у main та тегу v1.0.0.
5. Часткова перевірка журналу за ключовими словами не є повноцінним аналізом усіх способів логування токенів і персональних даних.
6. Production-like поведінку перевірено локально, а не на зовнішньому production deployment.
7. CSRF покриває лише ті маршрути, до яких фактично підключено перевірку; нові mutation endpoints потрібно перевіряти окремо.

## 11\. Conclusion

ЛР №6 продемонструвала системний характер захисту SecureLab: CSRF потребує коректної серверної перевірки й підтримки клієнта; rate limiting обмежує зловживання окремо від контролю доступу; аудит NuGet і Git допомагає виявляти ризики, які не проявляються в окремому HTTP-тесті; структуроване журналювання дозволяє відстежувати privileged transitions, не розкриваючи секрети. Реальні дефекти слід підтверджувати початковим станом, виправленням і повторним тестом. Відсутні докази залишено явно позначеними, без помилкової декларації повного PASS.
